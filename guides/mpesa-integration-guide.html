M-Pesa integration and payment evidence guide

This guide covers the integration principles required to process M-Pesa evidence safely. Follow the specific Daraja product documentation and PesaGuard's deployed contract for exact payload fields, callback signatures, routes and environment configuration.

Use the right PesaGuard surface: customers operate the product in app.pesaguard.co.ke; developers manage available integration workflows in developers.pesaguard.co.ke; requests go to the documented API at api.pesaguard.co.ke. Confirm actual endpoints and supported behavior in the OpenAPI contract.

1. Scope and source of truth

M-Pesa is the payment integration currently identified for PesaGuard. Exact product coverage depends on the deployed integration: do not assume every Daraja product, callback type, refund flow or account setup is enabled. Use the provider's current official integration instructions for provider-side configuration and PesaGuard's OpenAPI contract for PesaGuard-side operations.

2. Conceptual transaction flow

  1. A customer initiates a payment through the supported merchant flow.
  2. The provider processes the request and sends a callback or makes transaction evidence available according to the configured product.
  3. The receiver validates the request according to the provider's documented security model and validates the expected schema.
  4. The service associates the provider event with the correct tenant and business context using trusted configuration.
  5. The event is deduplicated using stable source identifiers and persisted durably.
  6. Transaction processing and reconciliation run according to the enabled workflow.
  7. The result becomes available to authorized Dashboard users and supported API consumers.
  8. Where configured, supported events notify external systems through verified webhooks.

3. Callback safety

  • Use HTTPS and the exact callback verification mechanism documented by the provider and current deployment.
  • Do not trust a callback merely because it contains a familiar transaction reference or expected amount.
  • Validate required fields, expected account/shortcode configuration, amount units, currency, transaction type and timestamps where applicable.
  • Enforce request size limits and safe parsing; reject malformed data with a controlled response.
  • Do not place provider secrets in client-side code, public repositories or logs.
  • Persist source event identity and processing state so a repeated callback does not create duplicate financial records.

4. Duplicate and out-of-order events

Callbacks can be retried, delayed or arrive after a later event. Use a stable provider transaction/event identifier and a durable uniqueness constraint where the provider contract guarantees uniqueness. If the callback does not uniquely identify an event, define a safe composite key and document its limitations. Keep reversals/refunds as related lifecycle events rather than erasing the original transaction.

5. Reconciliation inputs

Define how provider evidence maps to the merchant's order or ledger entry. Prefer an authoritative reference; use amount, currency, time window and account only as policy-approved secondary criteria. Do not automatically match ambiguous candidates. Preserve the source reference and matching-policy version so finance teams can explain an outcome later.

6. Failure handling

  • Callback rejected: investigate provider configuration, schema mismatch and authentication evidence without weakening validation.
  • Duplicate callback: return the documented acknowledgement and avoid repeating the side effect.
  • Timeout: determine whether the original event was persisted before retrying.
  • Provider unavailable: preserve pending work and resume through the supported retry/reconciliation mechanism.
  • Unmatched payment: inspect source completeness and internal ledger data before declaring a discrepancy.
  • Reversal or refund: represent the new event and update derived status under the documented state model.

7. Sandbox and production tests

  • Valid callback with representative synthetic values.
  • Missing or malformed required fields.
  • Duplicate callback delivered concurrently.
  • Unknown reference or tenant context.
  • Amount/currency mismatch and delayed ledger counterpart.
  • Timeout after durable persistence but before acknowledgement.
  • Reversal/refund and out-of-order event sequence where supported.
  • Credential rotation, callback URL change and incident recovery.

8. Production gate

Confirm the correct merchant/provider configuration, callback URL, secrets, source mapping, duplicate controls, reconciliation policy, monitoring, support owner and recovery procedure. Keep sandbox and production credentials separate. Do not enable live payment traffic until end-to-end tests, backups/recovery where relevant, and operational ownership are verified. The existence of this guide is not proof of a working provider integration.

9. Where developers work

Use developers.pesaguard.co.ke for enabled developer access, project and credential workflows. Use api.pesaguard.co.ke as the intended Core API origin, and confirm exact routes and schemas in the OpenAPI reference. Customer operators use the Customer Dashboard to review permitted operational records.
