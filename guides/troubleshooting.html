Troubleshooting and integration diagnostics

Troubleshoot from evidence: preserve request IDs, inspect the documented error schema, identify which layer failed, and avoid unsafe retries. This guide is a diagnostic method, not a substitute for endpoint-specific behavior in the live contract.

Contract-first rule: use developers.pesaguard.co.ke for the developer workflows that are enabled for your account. Confirm exact methods, paths, security schemes, request fields and response schemas in the published OpenAPI contract before calling api.pesaguard.co.ke. A documented design or domain name does not prove a feature is deployed.

1. Diagnose in a consistent order

  1. Record the approximate timestamp, environment, HTTP method, documented path, response status and request/correlation ID, if provided.
  2. Remove secrets and sensitive personal/financial values from diagnostic material before sharing it.
  3. Check whether the failure is transport/TLS, authentication, authorization, request validation, business-state conflict, rate limiting, downstream processing or webhook delivery.
  4. Compare the request to the exact operation in the OpenAPI reference.
  5. Check current incidents at the status site, but verify the issue from your own logs as well.
  6. Before retrying a mutation, establish whether the original operation may already have succeeded.

3. DNS, TLS and connection failures

  • Confirm the hostname is the intended environment and the DNS record resolves from the client network.
  • Verify certificate hostname, validity period and certificate chain; do not disable TLS verification as a workaround.
  • Check proxy/firewall rules, outbound HTTPS access, DNS cache and system clock.
  • Set connect and read timeouts appropriate to the operation; do not make unbounded requests.
  • Do not assume the root of api.pesaguard.co.ke is a health endpoint. Use the documented health path for the target deployment.

4. Authentication and permissions

Check that the credential belongs to the correct environment and is active. Confirm the documented authentication scheme and exact header format. If authentication succeeds but authorization fails, review the project's scope, tenant membership, resource ownership and production approval. Manage enabled credential workflows through the Developer Platform; do not try random headers or another tenant's identifiers.

5. Validation and business-state problems

  • Compare the JSON property names and types against the schema; distinguish omitted fields from explicit nulls.
  • Check timestamps, timezone, money units, currency and identifier normalization.
  • Check whether the resource is in a state that allows the requested transition.
  • Do not assume that a syntactically valid transaction is eligible to match or settle.
  • Use a synthetic fixture to reproduce the failure; never alter live financial data solely to make a test pass.

6. Timeout, retry and duplicate behavior

A timeout means the client did not receive a result in time; it does not prove the server did not complete the operation. For mutations, first use the documented idempotency key or status lookup if available. Avoid parallel retries with new idempotency keys. For reads, retry only within a bounded policy and respect rate limits.

7. Reconciliation differences

  • Confirm both source feeds cover the same business period and timezone.
  • Check source completeness, ingestion lag and pagination before comparing totals.
  • Compare currency and amount units, transaction type, reference normalization and duplicate treatment.
  • Inspect exception reason codes and candidate evidence; do not infer fraud from a mismatch alone.
  • Keep settlement confirmation separate from a reconciliation match.
  • When replaying data, preserve source IDs and use idempotent ingestion.

8. Webhook failures

  • Confirm the receiver is reachable over HTTPS and returns the documented acknowledgement within the expected timeout.
  • Verify signature calculation against the raw body and documented headers.
  • Check server clock if signed timestamps are used.
  • Inspect duplicate-event handling and durable storage errors.
  • Review the configured event subscription and the sender's actual delivery logs if available.
  • Use the documented replay workflow and ensure replay cannot repeat a downstream financial effect.

9. Build a safe support bundle

Include environment, UTC timestamp, method and path, HTTP status, request ID, sanitized response body, minimal redacted reproduction, expected versus actual behavior, and whether a retry was attempted. Remove bearer tokens, API keys, webhook secrets, personal identifiers and full payment payloads. Never include database dumps or production credentials in a support ticket.

10. Escalation

First check the relevant guide and API contract, then review the status page. If escalation is necessary, use the support/contact channel published by PesaGuard and send only the safe support bundle. A domain being linked from documentation does not guarantee that its current deployment is reachable.
