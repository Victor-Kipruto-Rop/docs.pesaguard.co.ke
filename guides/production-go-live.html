Production go-live and release readiness

Production readiness is a set of verifiable gates, not a button or a successful sandbox request. Use this checklist to establish that the integration, the API, the tenant configuration and the operating team are prepared for real financial workloads.

Contract-first rule: use developers.pesaguard.co.ke for the developer workflows that are enabled for your account. Confirm exact methods, paths, security schemes, request fields and response schemas in the published OpenAPI contract before calling api.pesaguard.co.ke. A documented design or domain name does not prove a feature is deployed.

1. Confirm access and environment

  • Developer identity and project ownership are verified through the enabled process in the Developer Platform.
  • Production access is explicitly approved under the current policy; sandbox credentials are not reused.
  • The tenant, allowed operations, callback URLs and credential grants match the approved workload.
  • The API origin and TLS certificate are verified in the target environment.
  • Any required M-Pesa/provider credentials are provisioned in the correct environment and are not committed to source control.

2. Contract and integration correctness

  • Pin the OpenAPI contract version or commit used for implementation.
  • Confirm every used method, path, request/response schema, enum, error code and security requirement against the current contract.
  • Test required and optional fields, boundary values, malformed values and unknown enum values.
  • Confirm idempotency behavior for every mutating operation before enabling automatic retries.
  • Define how the integration distinguishes accepted, processed, matched, failed, reversed and settled outcomes, based on actual supported states.
  • Verify pagination, rate-limit headers and retry guidance if provided.

3. Security review

  • Secrets are stored in an approved server-side secret store and redacted from logs.
  • Tenant isolation and resource-level permissions have positive and negative tests.
  • API keys are least privilege and revocation has been tested.
  • Webhook signature verification and deduplication are tested where webhooks are used.
  • Callback endpoints validate requests, enforce size/time limits and avoid open redirects or server-side request forgery patterns.
  • Sensitive exports and administrative actions are authorized and auditable.
  • Dependency, container and source scans have been reviewed according to the project's release policy.

4. Reliability and failure handling

  • Set explicit connection and response timeouts.
  • Retry only operations whose contract makes retry safe; use idempotency and bounded backoff with jitter.
  • Handle 401/403 without infinite retries; handle 429 using documented limits; treat 5xx/timeouts as potentially ambiguous for mutations.
  • Use durable queues and dead-letter handling if the integration is asynchronous.
  • Verify duplicate webhook handling and replay procedures.
  • Define degraded-mode behavior when the API, database, provider or event consumer is unavailable.

5. Observability and incident response

  • Log request IDs, event IDs, operation names and safe status codes; never log credentials or unnecessary personal/financial data.
  • Monitor error rates, latency, rate limits, ingestion freshness, reconciliation exceptions and webhook failures.
  • Set alerts with owners and actionable thresholds rather than paging on every transient failure.
  • Document who can revoke keys, disable an integration, pause ingestion and communicate an incident.
  • Know how to consult the status site, while remembering that it does not replace application monitoring.

6. Data and recovery

  • Establish the authoritative source for transaction evidence and reconciliation results.
  • Verify backup coverage, retention, restore procedure and recovery objectives for systems your team operates.
  • Rehearse reprocessing and reconciliation after a source outage without duplicating financial records.
  • Preserve original source references, policy versions and audit records during repair operations.
  • Define retention and deletion behavior according to documented legal, contractual and product requirements; do not assume an undocumented retention period.

7. Go/no-go decision

GateRequired evidenceBlock release if
ContractTested against current OpenAPI and target environment.Used paths or response semantics are guessed or drifting.
AccessCorrect production identity, tenant and grants verified.Sandbox credentials or unverified access are used.
Financial safetyDuplicate, timeout, retry and reversal scenarios tested.A retry can create duplicate financial effects.
IsolationCross-tenant and role-boundary tests pass.Unauthorized resource access is possible.
OperationsMonitoring, ownership, incident and recovery procedures tested.No one can detect or safely recover from failure.
ProviderProvider callbacks and credentials verified in the correct environment.Provider integration is assumed rather than tested.

8. After launch

Use a staged rollout where possible. Start with a bounded workload, compare source and PesaGuard totals, watch error and exception rates, and define a rollback or disable procedure before increasing volume. Review credential use and permissions regularly. Record the deployed contract version and operational owner. Production approval does not mean a system is permanently ready; each material change should repeat the relevant gates.

9. Where to perform each task

Use developers.pesaguard.co.ke for production-access workflows that are actually enabled. Use the OpenAPI reference for exact API semantics and send requests to api.pesaguard.co.ke. For business operations, use the authenticated Customer Dashboard. Do not infer approval, API reachability or live readiness from a successful documentation build.
