Customer Dashboard and Core API integration

The Customer Dashboard is an operational client, not a separate financial engine. It presents permitted records and submits user actions, while the Core API remains responsible for access checks, business rules and durable state changes.

Contract-first rule: use developers.pesaguard.co.ke for the developer workflows that are enabled for your account. Confirm exact methods, paths, security schemes, request fields and response schemas in the published OpenAPI contract before calling api.pesaguard.co.ke. A documented design or domain name does not prove a feature is deployed.

1. Keep responsibilities explicit

  • Dashboard frontend: navigation, accessible forms, filters, tables, charts, status labels and client-side input feedback.
  • Dashboard authentication layer: user session lifecycle, sign-in state and user experience for reauthentication.
  • Core API: authoritative identity validation, tenant authorization, business validation, persistence and audit events.
  • Workers and event services: long-running reconciliation, report generation and notification delivery when these are implemented as asynchronous jobs.
  • Database: authoritative persisted records; it must not be accessed directly from untrusted browser code.

2. Safe request path

  1. The user signs in through the deployed Dashboard authentication flow.
  2. The frontend requests data using the session or token mechanism explicitly supported by the backend.
  3. The API authenticates the user and resolves authorized tenant context server-side.
  4. The API applies resource-level authorization and returns only permitted records.
  5. For a mutation, the server validates the requested transition, persists the result and records the audit event.
  6. The UI refreshes from the authoritative response rather than assuming its local optimistic state is final.
Never put a privileged API key in frontend code. Any value shipped to the browser can be inspected. If the Dashboard needs server-to-server credentials, keep them in a trusted server-side layer and expose only narrow, authenticated application endpoints.

3. Tenant isolation is mandatory

Every list, detail, export, report, background job, webhook configuration and mutation must be checked against the authenticated user's grants. Hiding another tenant's row in the UI is not security. Test direct requests that substitute another tenant's identifier, resource ID, report ID and export URL.

  • Derive tenant context from authenticated server-side identity where possible.
  • Where a tenant selector is part of the UX, validate that the user is a member of the selected tenant on every request.
  • Ensure background jobs carry immutable tenant context and revalidate authorization at enqueue time.
  • Use least-privilege roles for viewing, resolving exceptions, exporting and administering members.
  • Keep audit history tenant-scoped and prevent users from editing or deleting evidence outside the supported workflow.

5. Loading, empty, partial and error states

  • Loading: show a stable skeleton or progress state; prevent duplicate submission while a mutation is pending.
  • Empty: distinguish “no records match these filters” from “no data has been ingested yet”.
  • Partial: show which source or time range is incomplete rather than displaying a misleading zero.
  • Unauthorized: clear stale client data and direct the user to reauthenticate or request access without revealing protected resource details.
  • Retryable failure: show a clear retry action and preserve safe form input where appropriate.
  • Mutation timeout: do not blindly repeat a financial mutation. Check its status using the documented workflow and idempotency semantics.

6. Performance and pagination

Use server-side pagination, filters and sorting for large histories. Prefer stable cursor pagination if provided by the contract. Avoid fetching all transactions into browser memory, creating one API request per table row, or recalculating financial totals from an incomplete page. Cache only data that is safe to cache, and invalidate it after relevant mutations. Respect rate limits and cancellation where supported.

7. Browser security and accessibility

  • Use HTTPS and secure session cookie attributes when cookie sessions are used; implement CSRF protection for cookie-authenticated state-changing requests as appropriate.
  • Do not store long-lived privileged secrets in local storage.
  • Use a restrictive Content Security Policy and safe output encoding; do not render API-provided strings as trusted HTML.
  • Provide keyboard-accessible tables, clear focus states, accessible validation messages and non-color-only status indicators.
  • Mask sensitive values by default and avoid exposing full payment identifiers unless required by the user's role.

8. Integration test matrix

  • Authorized user can view permitted records for their tenant.
  • User from a different tenant cannot read, update, export or infer the protected resource.
  • Viewer cannot perform administrator or exception-resolution actions.
  • Expired session and revoked credentials are handled without stale data leakage.
  • Duplicate form submission does not create duplicate financial records.
  • Timeout and retry behavior preserves the original operation identity.
  • Large date ranges and empty result sets remain responsive and accurate.
  • Audit history records sensitive operations and cannot be edited by ordinary users.
