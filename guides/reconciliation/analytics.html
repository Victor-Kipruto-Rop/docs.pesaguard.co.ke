Reconciliation guides

Analytics & reporting

Five endpoints, all GET, all read:discrepancies, all computed live from the discrepancy table on every call — there is no separate reporting store or nightly rollup. A discrepancy resolved a second ago is already reflected.

Numbers agree with the queue

Because every figure here is a live aggregate over the same rows the discrepancy list reads, a report and the underlying record can never drift out of sync the way a batch export can.

SLATRENDSREPORT

SLA metrics

How many critical discrepancies are on track, in warning or breaching their SLA right now — the same sla_status calculation the discrepancy list exposes per row, pre-aggregated into counts. Non-critical discrepancies are not counted at all: total here is the critical count, not every open discrepancy.

The three buckets may not sum to total. total is every critical discrepancy, resolved or not. A resolved one gets an internal status of resolved, which this endpoint doesn't add to any of on_track, warning or breaching — so on a tenant with resolved critical history, on_track + warning + breaching < total is expected, not a bug to chase.
GET/analytics/sla-metrics
GET /analytics/sla-metrics
Authorization: Bearer <token>
{ "on_track": 14, "warning": 2, "breaching": 1, "total": 17 }

Resolution times

Average, median and 95th-percentile resolution time in minutes, over every discrepancy that has both a detected_at and a resolved_at — unresolved discrepancies are excluded, not counted as infinite. With no resolved discrepancies yet, every field is 0, not null.

GET/analytics/resolution-times
GET /analytics/resolution-times
Authorization: Bearer <token>
{ "average_resolution_time": 182, "median_resolution_time": 96, "p95_resolution_time": 890 }

Operator stats

Per-assignee counts: how many discrepancies each operator has, how many they've resolved, and their average resolution time. Unassigned discrepancies are grouped under the literal string "Unassigned" as if it were an operator. Sorted by resolved_count, most first.

GET/analytics/operator-stats
GET /analytics/operator-stats
Authorization: Bearer <token>
Response shape. This route returns a bare JSON array, not an object with an items or similar wrapper key — different from every other list-shaped endpoint on this API.
[
  { "operator": "amina@yourcompany.com", "assigned_count": 12, "resolved_count": 9, "average_resolution_time": 145 },
  { "operator": "Unassigned", "assigned_count": 3, "resolved_count": 0, "average_resolution_time": 0 }
]

Incident trends

Two fixed-size time series: the last 4 calendar weeks and the last 12 calendar months, each bucket giving total, resolved and open (open is incidents - resolved for that bucket, not a separate query). Months are 30-day-wide buckets labelled by short month name, so two buckets can share a label in edge cases around month boundaries.

GET/analytics/incident-trends
GET /analytics/incident-trends
Authorization: Bearer <token>
{
  "weekly": [
    { "week": "W1", "incidents": 5, "resolved": 4, "open": 1 },
    { "week": "W2", "incidents": 8, "resolved": 6, "open": 2 },
    { "week": "W3", "incidents": 3, "resolved": 3, "open": 0 },
    { "week": "W4", "incidents": 6, "resolved": 2, "open": 4 }
  ],
  "monthly": [ { "month": "Jun", "incidents": 21, "resolved": 18, "open": 3 } ]
}

Neither window is configurable — there is no query parameter to ask for 8 weeks or 6 months. If you need a different range, use GET /analytics/reconciliation-report's days parameter, or aggregate from the CSV export yourself.

Reconciliation report

The one report endpoint with a configurable window, and the most complete single snapshot: totals, resolution rate, a breakdown by severity and by status, and two derived percentages.

GET/analytics/reconciliation-report
GET /analytics/reconciliation-report?days=30
Authorization: Bearer <token>
ParameterMeaning
daysLookback window by detected_at. Integer, 1–3650, default 7.
{
  "report_period_days": 30,
  "generated_at": "2026-09-26T10:00:00+00:00",
  "summary": {
    "total_incidents": 42,
    "resolved": 35,
    "open": 7,
    "resolution_rate": 0.833,
    "average_resolution_minutes": 210
  },
  "by_severity": { "critical": 6, "warning": 20, "info": 16 },
  "by_status": { "resolved": 35, "needs_review": 4, "missing_payment": 3 },
  "critical_count": 6,
  "sla_compliant_percentage": 83.3
}
Read sla_compliant_percentage carefully. It is computed as resolved / total, identical to resolution_rate expressed as a percentage — it is not derived from the same on-track/warning/breaching SLA calculation that SLA metrics and the discrepancy list use. A tenant with a low resolution rate but no active SLA breaches will still show a low number here.
