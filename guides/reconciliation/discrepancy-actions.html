Reconciliation guides

Discrepancy actions

A discrepancy is created automatically by the reconciliation engine. These seven endpoints are how a reviewer takes it from detected to resolved: read the queue, assign an owner, leave notes, resolve one or many, and export the current view.

The discrepancy record is the audit trail

Every action below appends to the same timeline and, for resolve and bulk-resolve, writes an audit event. There is no separate "actions log" to keep in sync.

All seven are scoped to the caller's tenant. A path parameter naming a discrepancy from a different tenant returns 404, not 403 — the record is not disclosed to exist.

Activity feed

The most recent discrepancies for the tenant, newest first, each reduced to its latest timeline entry. Read-only; nothing here is derived on the fly from an audit log, it is the record's own timeline field.

GET/activity-feed
GET /activity-feed?limit=5
Authorization: Bearer <token>
ParameterMeaning
limitInteger, 1–100, default 5.
{
  "items": [
    {
      "id": "disc-8f2c...",
      "event": "note_added",
      "message": "Waiting on the provider's own investigation.",
      "severity": "warning",
      "timestamp": "2026-09-20T09:14:02+00:00",
      "trans_id": "QGH7XABC12"
    }
  ]
}

event is whichever of created, note_added, resolved or bulk_resolved was appended most recently by the actions below. A discrepancy with an empty timeline (never happens through normal use, but possible on old data) is reported as created.

Assignment queue

Every open (unresolved) discrepancy for the tenant, newest first — the working list for a reviewer deciding what to pick up next.

GET/assignment-queue
GET /assignment-queue
Authorization: Bearer <token>
{
  "items": [
    {
      "id": "disc-8f2c...",
      "trans_id": "QGH7XABC12",
      "severity": "critical",
      "assignee": "Unassigned",
      "queue_status": "needs_assignment",
      "anomaly_type": "missing_payment",
      "detected_at": "2026-09-20T09:00:11+00:00"
    }
  ]
}

queue_status is derived, not stored: it is assigned when the record has an assignee and needs_assignment otherwise. There is no separate "unassign" endpoint — POST /discrepancies/{id}/assign with an empty assignee string is how you clear one; the route logs that explicitly as "Assignment cleared" rather than "Assigned to ".

Resolve one discrepancy

Marks a single discrepancy resolved, stamps resolved_at, and records an audit event for it.

POST/discrepancies/{discrepancy_id}/resolve
POST /discrepancies/{discrepancy_id}/resolve
Authorization: Bearer <token>
Content-Type: application/json

{
  "note": "Confirmed with the provider: late settlement, now posted."
}

note is optional; when given, it replaces resolution_note on the record (it does not append to the running notes field the way POST /discrepancies/{id}/notes does). Response:

{ "status": "resolved", "id": "disc-8f2c..." }
StatusMeaning
404No discrepancy with that id in the caller's tenant.
415Body was not sent as application/json.

Bulk resolve

Resolves several discrepancies in one call with a shared note, and writes one audit event for the whole batch listing every id it touched — not one event per row, since a bulk action is one operator decision.

POST/discrepancies/bulk-resolve
POST /discrepancies/bulk-resolve
Authorization: Bearer <token>
Content-Type: application/json

{
  "ids": ["disc-8f2c...", "disc-91ab..."],
  "note": "Batch cleared after the provider's settlement replay."
}
FieldRequiredNotes
idsYesArray of discrepancy ids.
noteNoDefaults to "Bulk resolved".
{ "status": "resolved", "updated": 2, "skipped_ids": [] }

An id that does not exist in the caller's tenant is not an error for the batch: it is added to skipped_ids and everything else in the request still resolves. Requires bulk:operations, a distinct, broader permission from the write:discrepancies the single-item endpoints use — a role can have one without the other.

Assign

Sets who owns a discrepancy. There is one field, and it is required.

POST/discrepancies/{discrepancy_id}/assign
POST /discrepancies/{discrepancy_id}/assign
Authorization: Bearer <token>
Content-Type: application/json

{ "assignee": "amina@yourcompany.com" }
{ "status": "assigned", "assignee": "amina@yourcompany.com" }

assignee is a free-text string on this record; it is not validated against a user or team directory. If you need assignment restricted to real accounts, enforce that in the caller before sending the request. assignee is required as a field, but an empty string is a valid value and is how you unassign — the timeline records it as "Assignment cleared" rather than "Assigned to ".

Add a note

Appends one line to the discrepancy's running notes field and to its timeline. Unlike resolve's optional note, this one is required and additive — it never overwrites what's already there.

POST/discrepancies/{discrepancy_id}/notes
POST /discrepancies/{discrepancy_id}/notes
Authorization: Bearer <token>
Content-Type: application/json

{ "note": "Provider confirms the reversal posted at 14:02." }
{ "status": "saved", "notes": "- Provider confirms the reversal posted at 14:02." }

An empty or whitespace-only note is accepted by validation but has no effect: nothing is appended and notes is returned unchanged. Send a non-empty string to actually record something.

Export as CSV

The same filters as the discrepancy list, returned as a CSV file instead of a paginated JSON envelope — every matching row in one response, capped only by how many discrepancies the tenant has.

GET/discrepancies/export/csv
GET /discrepancies/export/csv?status=missing_payment&severity=critical
Authorization: Bearer <token>
ParameterValues
statusneeds_review, assigned, resolved, open, closed, pending, missing_payment, missing_transaction, amount_mismatch, duplicate
severitycritical, warning, info
resolvedopen or resolved

Columns: id, trans_id, anomaly_type, severity, status, resolved, tenant_id, assignee, detected_at, resolved_at, notes. resolved is written as Yes/No; empty assignee and tenant_id are written as Unassigned and N/A rather than left blank. This route needs an authenticated tenant context and returns 403 without one — unlike the JSON list and activity feed, which fall back to an unscoped query when no tenant is resolved.
