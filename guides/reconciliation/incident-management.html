Incident management

Discrepancies are called "incidents" on this set of endpoints — same underlying record, four operations for working a queue rather than one row: full-text search, bulk assignment, time-based auto-escalation, and saved filter presets.

All four require bulk:operations or read:discrepancies

None of these use write:discrepancies, the permission the single-item actions need — a role built for triage doesn't need per-item write access.

SEARCHASSIGNESCALATE

Search incidents

Full-text-ish search across trans_id, anomaly_type and notes (a SQL LIKE match, not a search index), with severity and assignee filters and real pagination. This is the one to use for "find the incident I'm thinking of" — the plain discrepancy list only filters on exact fields.

GET/incidents/search
GET /incidents/search?q=QGH7X&severity=critical&page=1&per_page=20
Authorization: Bearer <token>
ParameterNotes
qMatched against trans_id, anomaly_type, notes. Max 200 characters.
severitycritical, warning or info.
assigneeExact match, not a substring search. Max 200 characters.
page / per_pageDefault 1 / 20; per_page caps at 100.
{
  "query": "QGH7X",
  "page": 1,
  "per_page": 20,
  "total": 1,
  "items": [
    { "id": "disc-8f2c...", "trans_id": "QGH7XABC12", "anomaly_type": "missing_payment", "severity": "critical", "assignee": "Unassigned", "detected_at": "2026-09-20T09:00:11+00:00" }
  ]
}

Unlike GET /discrepancies, this route requires a resolved tenant context and returns 403 without one.

Bulk assign

Assigns many incidents to one owner in one call, the assignment equivalent of bulk-resolve: same ids / skipped_ids shape, one timeline entry per incident (not one audit event per batch — this route does not call the audit trail the way resolve and bulk-resolve do).

POST/incidents/bulk-assign
POST /incidents/bulk-assign
Authorization: Bearer <token>
Content-Type: application/json

{
  "ids": ["disc-8f2c...", "disc-91ab..."],
  "assignee": "amina@yourcompany.com",
  "note": "Reassigning after amina's shift handover"
}
FieldRequired
idsYes
assigneeYes
noteNo — defaults to "Bulk assigned". Folded into each timeline entry's message, not stored as a separate field.
{ "status": "assigned", "updated": 2, "skipped_ids": [] }

Auto-escalate

A sweep, not a per-item action: finds every unresolved, critical, currently unassigned incident older than a threshold and assigns it to a fixed literal owner, "On-Call Lead" — there is no way to configure who that is per tenant today. An incident that already has an assignee is left alone even if it is old and critical.

POST/incidents/auto-escalate
POST /incidents/auto-escalate?escalation_minutes=45
Authorization: Bearer <token>
ParameterMeaning
escalation_minutesAge threshold. Integer, 1–10080 (one week), default 45.
{ "status": "escalated", "count": 3, "threshold_minutes": 45 }

This is a synchronous sweep triggered by the caller, not a background job — call it on a schedule (a cron hitting this endpoint every few minutes) if you want continuous auto-escalation rather than a one-off catch-up run.

Filter presets

Not durable. POST here does not write to a database or any other store. The preset dictionary is a local variable rebuilt fresh on every single request, so a preset "saved" by one call is gone by the next — including the next call from the same client. Do not build a "my saved filters" feature on this endpoint; it always returns to the three built-in presets. For filters that actually persist, see the communications module's saved-filters endpoints, which are backed by a real table.
GET/incidents/filters/presets
GET /incidents/filters/presets
Authorization: Bearer <token>
{
  "presets": {
    "critical_open": { "severity": "critical", "resolved": "open" },
    "needs_review": { "status": "needs_review" },
    "all": {}
  }
}
POST/incidents/filters/presets
POST /incidents/filters/presets
Authorization: Bearer <token>
Content-Type: application/json

{ "name": "my_view", "filters": { "severity": "warning" } }

Returns 201 with the (still request-local) preset dictionary including the one just added. GET only needs read:discrepancies, but POST additionally checks for write:discrepancies in the handler itself rather than in the route decorator — the two methods on this one route do not share a single permission requirement.
