Webhook engineering and event consumers

Webhooks help external systems react to supported PesaGuard events. Reliable integrations treat each delivery as untrusted input, verify authenticity, tolerate duplicates, persist before acknowledging and reconcile webhook observations against authoritative API state.

Contract-first rule: use developers.pesaguard.co.ke for the developer workflows that are enabled for your account. Confirm exact methods, paths, security schemes, request fields and response schemas in the published OpenAPI contract before calling api.pesaguard.co.ke. A documented design or domain name does not prove a feature is deployed.

1. Verify the event capability first

Use the OpenAPI contract and the webhook documentation to confirm whether webhook configuration, the requested event type, signature headers and delivery inspection are actually supported. Manage the enabled configuration workflow at developers.pesaguard.co.ke. Do not invent event names, headers, retry intervals or signing algorithms.

2. Design for at-least-once delivery

Network failures create ambiguity: a consumer may process an event successfully but fail before the sender receives the acknowledgement. The sender may retry, so the same event can arrive more than once. Consumers must be idempotent. Delivery order may also differ from business-event order unless the contract explicitly guarantees ordering.

3. Receiver processing sequence

  1. Accept HTTPS requests only on the intended route and enforce a request-size limit.
  2. Read the raw request body exactly as received if signature verification depends on raw bytes.
  3. Verify the documented signature and timestamp/replay window before trusting event contents.
  4. Validate content type, schema version, event identifier, event type and required fields.
  5. Atomically record the event identifier in a deduplication store and persist the accepted delivery.
  6. Return the documented successful acknowledgement promptly after durable acceptance.
  7. Process business logic asynchronously from the durable record; isolate retries from the request thread.
  8. Record success, permanent failure or retry state with correlation identifiers and redacted diagnostics.

4. Signature verification

Follow the exact algorithm, canonicalization and header names documented for the deployed integration. Common implementation mistakes include verifying a parsed-and-reserialized JSON body instead of the original bytes, comparing signatures with ordinary string equality, ignoring timestamps, accepting unsigned payloads in production, and logging the signing secret.

  • Use constant-time comparison where the signature scheme requires it.
  • Reject invalid signatures before performing business actions.
  • Keep signing secrets outside source control and rotate them using the supported process.
  • Use a documented replay window if timestamps are part of the signature scheme.
  • Test key rotation, stale timestamps, malformed encodings and duplicate delivery.

5. Idempotency and deduplication

Use the provider's stable event ID as the primary deduplication key when guaranteed by the contract. Scope the key appropriately to the sender/account/environment if IDs are not globally unique. Enforce uniqueness in durable storage, not only in process memory. If an event causes a mutation in another system, make that mutation idempotent too; deduplicating the inbound HTTP request alone does not prevent downstream duplicates.

receive request
  -> verify signature
  -> validate schema
  -> insert event_id with unique constraint
       -> inserted: persist event, acknowledge, process
       -> duplicate: acknowledge safely without repeating side effect
       -> storage failure: do not claim durable acceptance

6. Retries, backoff and dead letters

Use the retry policy published for the actual sender. If you control the consumer's internal retry, use bounded exponential backoff with jitter, cap attempts or elapsed time, distinguish transient from permanent failures, and move exhausted work into an inspectable dead-letter state. Do not invent an upstream retry schedule when one is not documented.

  • Transient: network reset, temporary dependency outage, rate limit where retry is allowed.
  • Permanent: invalid signature, unsupported schema version, malformed required field or business rejection that cannot succeed unchanged.
  • Ambiguous: timeout after a downstream side effect. Query the downstream state or use idempotency before replay.

7. Replay and ordering

Replay should reuse the stable event identity and be visible in operational logs. A replay tool must require authorization, preserve the original payload and event timestamp, and record who initiated it. Do not assume events arrive in order. If ordering matters, use sequence/version fields when provided, detect stale updates, and retrieve current resource state from the Core API when needed.

8. Monitoring and alerting

  • Delivery attempts, success ratio and latency.
  • Age and count of pending events.
  • Signature failures and invalid schema rate.
  • Duplicate rate and deduplication-store errors.
  • Retry count, dead-letter count and oldest failed item.
  • Consumer processing lag and downstream error rate.

Never put payment details, bearer credentials or signing secrets in logs. Correlate by event/request IDs where available and provide a safe way to inspect delivery state in the Developer Platform if that capability is implemented.

9. Required test cases

  • Valid signature and valid schema.
  • Invalid signature, wrong secret, altered body and stale timestamp where applicable.
  • Same event delivered twice concurrently.
  • Receiver crash after persistence but before acknowledgement.
  • Database unavailable during acceptance.
  • Downstream timeout after a successful side effect.
  • Out-of-order and unsupported-version events.
  • Large payload, unexpected content type and rate-limited sender.
  • Replay from a dead-letter state with audit traceability.
