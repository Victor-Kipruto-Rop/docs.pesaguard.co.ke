Authentication guides

API keys

Request API keys through the deployment's authorized operator workflow. Keys identify a workload; their stored tenant, role, explicit scopes, active/revoked state, and optional expiry determine whether the API accepts and authorizes them.

Credential rule

Separate ownership limits blast radius and makes rotation and compromise response measurable.

Before provisioning

  • Name the integration and owner.
  • Select environment and tenant.
  • List required actions and request the narrowest supported role/scopes.
  • Set an expiry and rotation policy, even though expiry is optional in the record.

Use the key safely

X-API-Key: $PESAGUARD_API_KEY
Accept: application/json

Send the key only over HTTPS. Store it in an approved server-side secret manager, and log the key identifier and request ID rather than the key value.

Verify access

  1. Make a read-only request in the intended non-production tenant.
  2. Confirm the response belongs to that tenant.
  3. Test an operation outside the key's effective permissions and confirm it is denied.
  4. Record the request ID and result before enabling writes.

Rotation and revocation

Coordinate replacement with the deployment operator; the canonical dashboard API does not expose a public key-issuance route. For planned rotation, deploy and verify the replacement before revoking the old key when overlap is supported. If exposure is suspected, request revocation immediately, then review recent use and issue a replacement through the approved workflow.

See API key security for verifier behavior, scope intersection, key-record fields, and incident-response steps.
