Customer Dashboard operations handbook

A practical operating manual for finance teams and managers. It explains how to investigate a transaction, interpret reconciliation states, manage exceptions and reports, and avoid treating incomplete evidence as a final financial outcome.

Use the right PesaGuard surface: customers operate the product in app.pesaguard.co.ke; developers manage available integration workflows in developers.pesaguard.co.ke; requests go to the documented API at api.pesaguard.co.ke. Confirm actual endpoints and supported behavior in the OpenAPI contract.

1. Who this handbook is for

This guide is for authorized finance officers, operations analysts, supervisors and business administrators. It describes operational decision-making rather than promising that every screen or role is already enabled. The actual controls shown in your account and the current product release determine available actions.

2. A disciplined daily operating loop

  1. Check service condition. Review the published status page and any internal notices before interpreting a sudden absence of transactions as a business issue.
  2. Confirm source freshness. Identify the latest successfully ingested provider or ledger time. An empty view may indicate delayed ingestion or filters, not zero business activity.
  3. Review transaction exceptions. Sort by age, value and reason if those filters are available. Prioritize urgent exceptions under your organization's policy.
  4. Inspect source evidence. Compare provider references, internal order/ledger references, amount, currency, time and transaction state.
  5. Resolve only with evidence. Use the approved action, record the reason, and do not manually mark a transaction matched merely to clear a queue.
  6. Review reports and audit trail. Confirm the report period, timezone, currency and completeness before sharing totals.
  7. Escalate unresolved discrepancies. Preserve identifiers and a sanitized evidence bundle for the authorized support path.

3. Investigate a transaction

  1. Search by a stable reference or use date/status filters if supported.
  2. Open the authorized transaction detail and confirm its identity and tenant context.
  3. Compare the source/provider reference with the internal record reference.
  4. Check amount and currency together. Never compare values that use different units or currencies without a documented conversion policy.
  5. Review timestamps with their source timezone and ingestion time.
  6. Read the explicit transaction and reconciliation states; do not infer settlement from a successful API response.
  7. Review the available event history and audit information before changing anything.

4. Interpret statuses carefully

5. Handle an exception

  • Read the reason code and inspect both sides of the comparison.
  • Check for delayed source records before deciding that the counterpart is missing.
  • Look for duplicate source references, partial payments, refunds, reversals or a currency/amount-unit mismatch.
  • Do not force a match if more than one candidate fits.
  • Use only the role-authorized resolution action. Add a reason or note if the workflow requires it.
  • Confirm the resulting state and audit entry after the action completes.

6. Reports and exports

Before exporting, confirm date range, timezone, tenant, currency and filters. Determine whether totals include only matched records or also pending, failed, reversed or exception records. Avoid summing different currencies into one number without an explicitly documented conversion basis. Treat exports as sensitive records and share them only with authorized recipients.

7. Team and permissions

Use least privilege: viewers should not be able to administer members or resolve exceptions; finance operators should have only the actions needed for their duties; administrators should be tightly restricted. Never share a login or API secret. If a teammate loses access, use the supported access-management workflow rather than borrowing another person's account.

8. When to escalate

Escalate if a discrepancy persists after source freshness and filters are verified, if a sensitive action appears unexpectedly, if data crosses tenant boundaries, or if transaction states contradict provider evidence. Include the timestamp, environment, transaction/reference ID, sanitized status and request ID if available. Never send passwords, API keys, signing secrets or full personal/financial payloads in a support ticket.
