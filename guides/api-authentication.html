Security · Identity and access

API authentication and credential safety

Authentication establishes who or what is calling. Authorization determines what that caller may access. Both must be enforced by the Core API, even when requests originate from the Developer Platform or Customer Dashboard.

Contract-first rule: use developers.pesaguard.co.ke for the developer workflows that are enabled for your account. Confirm exact methods, paths, security schemes, request fields and response schemas in the published OpenAPI contract before calling api.pesaguard.co.ke. A documented design or domain name does not prove a feature is deployed.

1. Start with the supported authentication scheme

Open the OpenAPI contract and inspect the security requirements for the exact operation. Do not assume every route accepts a bearer API key. Some user-facing routes may use session cookies or another scheme. Use the Developer Platform to obtain credentials through the currently enabled workflow.

# Illustrative only: use the exact scheme and endpoint from OpenAPI.
curl --request GET \
  --url 'https://api.pesaguard.co.ke/REPLACE_WITH_DOCUMENTED_PATH' \
  --header 'Authorization: Bearer $PESAGUARD_API_KEY' \
  --header 'Accept: application/json'

This template intentionally does not name a concrete endpoint. Replace the path and headers only after confirming the deployed contract. Do not paste real secrets into shell history, screenshots, tickets, chat, or source control.

2. Authentication is not authorization

A valid credential proves that the caller controls a credential. It does not grant unrestricted access. The API should evaluate at least the following context where relevant to the implemented model:

  • Credential status: active, expired, revoked or otherwise invalid.
  • Environment: sandbox and production must be isolated.
  • Project or client association, if the Developer Platform uses projects.
  • Tenant association and resource ownership, resolved from trusted server-side data.
  • Scopes, roles or operation-level grants supported by the service.
  • Operational restrictions such as rate limits, production approval and risk controls.

Never authorize access solely from a caller-supplied tenant_id, organization name, role, or environment string. If the request includes such a value, compare it with the authenticated principal's grants and resource ownership.

3. Store secrets safely

  • Keep API keys in server-side environment configuration or a secrets manager; use least-privilege file and runtime permissions.
  • Do not include a secret in frontend bundles, mobile app packages, public repositories, query parameters, analytics events or client-visible error messages.
  • Use separate credentials for local development, CI, staging and production. Do not share personal credentials across team members.
  • Restrict who can view or rotate production credentials and record security-relevant changes.
  • Redact authorization headers and secret-bearing environment variables from logs, traces and crash reports.

4. Rotate or revoke a compromised key

  1. Identify the affected credential and the environment/project it can access.
  2. Use the supported key-management workflow in the Developer Platform or the authorized administrative process to revoke it. If self-service revocation is unavailable, follow the verified support/security escalation route.
  3. Create a replacement credential with only the necessary grants.
  4. Deploy it to the server-side secret store, restart or reload consumers as required, and verify a harmless request against the correct environment.
  5. Review audit and request logs for unexpected use during the exposure window. Rotate any other secrets that were exposed with it.
  6. Confirm the old key no longer works, then document the incident without copying the secret into the report.

5. Sandbox and production are separate security domains

ControlSandboxProduction
DataSynthetic or explicitly isolated test recordsAuthorized live business records
CredentialsTest-only credentialsSeparately issued and approved credentials
PermissionsLimited to test operationsLeast privilege for the approved workload
CallbacksTest endpoints and test secretsVerified production receiver and production signing material
ReleaseUsed to validate behaviorRequires release and operational readiness checks

Only describe staging or production key creation as available if the corresponding environment and workflow are actually deployed. A UI label or roadmap item is not evidence of provisioning.

6. Interpret authentication errors

  • 401: missing, malformed, expired or revoked credentials, or wrong authentication scheme.
  • 403: recognized identity but insufficient scope, role, tenant grant, environment access or approval.
  • 404: resource does not exist, or the service intentionally hides resources the caller is not allowed to see.
  • 429: rate or usage limit; use documented retry guidance.

Check the actual response body and request ID, if provided, before deciding the cause. Avoid retry loops for deterministic authentication failures.

7. Credential review checklist

  • Credential never reaches a browser or client-side source bundle.
  • Scope and tenant grants are tested with both allowed and forbidden examples.
  • Revocation takes effect within the documented operational expectation.
  • Rotation is rehearsed and does not require posting secrets in tickets.
  • Logs redact credential material and personal/financial data not required for diagnosis.
  • Sandbox credentials cannot read or mutate production data.
  • Production access and credential changes produce an auditable event where implemented.
