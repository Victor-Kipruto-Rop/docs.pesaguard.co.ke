Data quality, ingestion and source completeness

Reliable reconciliation starts before matching. This guide defines how to reason about source quality, detect missing or malformed records, preserve evidence and communicate data completeness without hiding uncertainty.

Use the right PesaGuard surface: customers operate the product in app.pesaguard.co.ke; developers manage available integration workflows in developers.pesaguard.co.ke; requests go to the documented API at api.pesaguard.co.ke. Confirm actual endpoints and supported behavior in the OpenAPI contract.

1. Data quality dimensions

DimensionQuestionUseful evidence
ValidityDoes each record satisfy its schema and business constraints?Invalid-field counts, rejected-record reasons, schema version.
CompletenessDid the expected source records arrive for the period?Source sequence/cursor, expected counts, ingestion checkpoints, missing windows.
UniquenessDid retries or replay create duplicate logical records?Stable source IDs, duplicate keys, idempotency outcomes.
ConsistencyDo amount, currency, timestamps and references agree across related records?Cross-source comparisons and canonicalization rules.
TimelinessDid records arrive within the expected freshness window?Event time vs ingestion time, lag distribution and last successful checkpoint.
TraceabilityCan a result be traced back to source evidence and transformations?Source identifiers, rule version, request/event IDs and audit trail.

2. Ingestion lifecycle

  1. Receive. Authenticate the source where required and enforce payload size/time limits.
  2. Validate envelope. Check content type, schema version, required identifiers and timestamp formats.
  3. Preserve provenance. Record source system, external reference and received time; preserve raw evidence under the documented retention and privacy rules.
  4. Normalize. Convert to a canonical model using versioned, testable transformations.
  5. Deduplicate. Apply a stable uniqueness key and record duplicate outcomes.
  6. Persist durably. Commit the source record and the corresponding idempotency/audit state before acknowledging success where the design requires durable acceptance.
  7. Publish downstream. Use a durable event/outbox pattern when applicable; monitor processing lag and failures.
  8. Reconcile. Run the matching policy only after inputs meet its prerequisites.

3. Canonicalization rules

  • Represent money with integer minor units or decimal-safe types and an explicit currency code.
  • Preserve original timestamps and normalize to a documented UTC representation for comparisons; display local time with an explicit timezone.
  • Keep raw references alongside normalized references. Only trim, case-fold or remove separators if the source contract guarantees that operation is safe.
  • Separate source event time, ingestion time, processing time and settlement time.
  • Distinguish missing, null, zero and empty-string values.
  • Version transformations so historical outcomes can be explained and safely reprocessed.

4. Data quality rules and thresholds

Each rule should have an owner, scope, severity, threshold, evaluation window, exception behavior and remediation path. Examples include required-field completeness, duplicate rate, invalid currency, out-of-range timestamps, unexpected amount precision, stale source feed and event-sequence gaps. Do not invent a threshold that is not approved for the business context.

5. Quarantine instead of silent loss

Malformed or suspicious records should enter a controlled rejected/quarantine path with a reason code and safe evidence reference. Do not silently discard records or automatically “repair” a financial amount. Any correction should be explicit, authorized, auditable and linked to the original source record. Protect quarantine views because raw payloads may contain sensitive data.

6. Freshness and completeness monitoring

  • Last successful fetch/ingestion time per source.
  • Expected versus observed record counts when the source provides a reliable expectation.
  • Lag from source event time to ingestion and from ingestion to processing.
  • Missing sequence numbers or cursor gaps when supported by the source.
  • Rejected, duplicated, retried and dead-lettered record counts.
  • Unusual shifts in record volume, amounts or transaction-type distribution.

Make the reporting denominator explicit. If a source feed is delayed or incomplete, show that limitation next to match-rate and financial totals instead of presenting partial results as complete.

7. Investigate a quality incident

  1. Determine the affected source, tenant, time window, environment and transformation version.
  2. Compare source counts/checkpoints with the ingested and processed counts.
  3. Identify whether the problem is missing data, malformed input, duplicates, ordering, normalization or downstream processing.
  4. Stop unsafe automatic retries if they can create duplicate side effects.
  5. Preserve a sanitized sample and trace identifiers.
  6. Repair the source or transformation, then replay through idempotent processing and verify counts and reconciliation outcomes.
  7. Document impact, root cause, remediation and follow-up monitoring.

8. Source support and integrations

Use the current integration configuration and API contract to determine which sources are enabled. PesaGuard's currently stated payment integration is M-Pesa; do not assume Airtel Money, bank feeds or POS connectors are available merely because they appear in a roadmap or conceptual model. Developers should manage supported integration workflows at developers.pesaguard.co.ke and verify actual operations against the OpenAPI contract for api.pesaguard.co.ke.
