Platform lifecycle and architecture

A system-level guide to how an integration is provisioned, how an API call is authorized and processed, how results reach the customer experience, and which PesaGuard surface owns each responsibility.

Contract-first rule: use developers.pesaguard.co.ke for the developer workflows that are enabled for your account. Confirm exact methods, paths, security schemes, request fields and response schemas in the published OpenAPI contract before calling api.pesaguard.co.ke. A documented design or domain name does not prove a feature is deployed.

1. The six surfaces and their ownership

SurfaceWhat it ownsWhat it must not become
Public siteProduct explanation, trust information, contact and onboarding entry points.A place to store privileged credentials or execute financial business rules in browser code.
Developer PlatformDeveloper identity and integration workspace; credential, environment, webhook and go-live workflows where implemented.The source of truth for transaction state or a bypass around API authorization.
Core APIServer-side contract, validation, tenant authorization, business operations, durable state transitions and integration responses.A thin proxy that trusts client-supplied tenant IDs or browser decisions.
Customer DashboardBusiness-facing views, transaction investigation, exception resolution, alerts, reports and team workflows where implemented.A privileged database client or the sole place where authorization is enforced.
DocumentationContract descriptions, examples, guides, error semantics, migration notes and supportable troubleshooting.A request proxy, credential issuer, or independent authority for live API behavior.
Status sitePublished availability and incident communication, subject to its actual deployment.A substitute for application-level timeouts, retries, health checks or observability.

2. End-to-end lifecycle

  1. Provision access. A developer visits the Developer Platform, completes the supported onboarding and creates or requests the appropriate environment credential.
  2. Read the contract. The developer checks the OpenAPI reference for the exact endpoint, security scheme, schema and errors.
  3. Send a request. Their server sends HTTPS to the documented API origin. Secrets remain server-side; the browser never receives a server-to-server API key.
  4. Authenticate and authorize. The Core API validates the credential and derives tenant/project/environment context from trusted server-side records. It rejects access outside the credential's grants.
  5. Validate and persist. Input validation, business invariants, idempotency and durable state updates run server-side. Long-running work may be asynchronous if the contract says so.
  6. Return a traceable result. The API responds with documented status and payload; clients log a request identifier where provided, without logging secrets or unnecessary personal data.
  7. Expose and notify. Authorized Dashboard users see permitted records. Configured webhooks can notify external systems; consumers verify and deduplicate delivery.
  8. Operate and improve. Developers monitor errors and usage, rotate credentials, test recovery, and review changelog and status communications.

3. Trust boundaries

  • Browser input, webhook payloads, uploaded statements, provider callbacks and caller-supplied identifiers are untrusted until verified.
  • Tenant isolation must be enforced on every query and mutation, not only by hiding UI controls.
  • Secrets are stored and used on server-side systems. Documentation examples use placeholders and synthetic identifiers.
  • Webhook delivery is at-least-once in many systems; consumers must tolerate duplicates even if the implementation also attempts deduplication.
  • Reconciliation outcomes, fraud signals and settlement status are different concepts and should not be collapsed into a single “success” flag.

4. Which source wins when information differs?

For exact request shape, use the current OpenAPI contract and verify it against the deployed API. For actual developer onboarding or key management, use the workflows exposed by the Developer Platform. For operational behavior, the backend implementation and deployment configuration are authoritative. Documentation is a maintained explanation, and any mismatch should be reported and corrected.

5. Integration design decisions

  • Keep business logic in the Core API or dedicated backend services; do not duplicate matching rules independently in each client.
  • Make request and event identifiers stable enough to support investigation and idempotent processing.
  • Separate sandbox and production credentials, records, queues, callbacks and permissions.
  • Use explicit lifecycle states and reason codes so finance teams can explain why a record matched or became an exception.
  • Version the API contract and publish breaking changes with migration instructions.
