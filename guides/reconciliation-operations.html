Reconciliation operations and exception handling

A reconciliation system should produce explainable outcomes, preserve source evidence and make unresolved differences visible. This guide describes the operational model without pretending every matching algorithm or endpoint is already enabled.

Contract-first rule: use developers.pesaguard.co.ke for the developer workflows that are enabled for your account. Confirm exact methods, paths, security schemes, request fields and response schemas in the published OpenAPI contract before calling api.pesaguard.co.ke. A documented design or domain name does not prove a feature is deployed.

1. What reconciliation proves—and what it does not

Reconciliation compares records that are expected to represent the same business event: for example, a payment-provider transaction and a merchant's order or ledger entry. It determines whether the available records agree under the configured matching policy. A match does not by itself prove settlement, and an unmatched record is not automatically fraud.

2. Required input discipline

Before matching, define the authoritative source and expected schema for each feed. Depending on the integration, useful fields may include provider transaction reference, internal order or ledger reference, amount in integer minor units, currency, event/booking timestamp, payer or account reference, transaction type, status, and source provenance. The exact required fields are defined by the deployed integration contract.

  • Preserve the original source payload or a governed evidence reference where lawful and necessary; store normalized values separately.
  • Normalize timestamps to a documented timezone convention while retaining original provider timestamps.
  • Use decimal-safe or integer-minor-unit arithmetic; never use binary floating point for money comparisons.
  • Normalize identifiers carefully. Do not strip characters or change case unless the source contract says those transformations are safe.
  • Record source system, ingestion time, source event time, and a stable source record identifier.
  • Reject or quarantine malformed records with a reason rather than silently dropping them.

3. Matching sequence

  1. Validate. Confirm schema, required values, supported currency and acceptable business state.
  2. Deduplicate. Use a stable provider/source identifier and documented idempotency rule to prevent repeated delivery becoming duplicate financial records.
  3. Normalize. Create canonical fields while preserving source evidence.
  4. Apply deterministic keys first. Where an authoritative reference exists, prefer it over a loose heuristic.
  5. Apply configured secondary criteria. Amount, currency, date window, account, transaction type or other policy-approved fields may narrow candidates.
  6. Resolve ambiguity. If multiple candidates satisfy the rule, flag an exception rather than arbitrarily selecting one.
  7. Persist the outcome. Store status, rule/version, evidence references, timestamps and reason codes.
  8. Publish the result. Expose it through authorized reads and supported events; preserve the ability to audit later changes.

4. Use explicit, non-overlapping states

Use the exact status names and transitions exposed by the current API contract. This table is a conceptual guide, not a claim that every state is a live enum.

5. Exception queue and investigation

An exception record should help a finance officer answer: what did we expect, what arrived, why did matching fail, what evidence is available, who is allowed to resolve it, and what happened afterward?

  • Show source references and safely masked identifying details.
  • Explain the specific mismatch: missing counterpart, amount mismatch, currency mismatch, date-window mismatch, duplicate, conflicting candidate or invalid input.
  • Allow assignment and notes only if the current product implements them.
  • Require an authorized resolution action and a reason when appropriate.
  • Record the actor, timestamp, previous state, new state and evidence references in an append-only or otherwise tamper-evident audit design.
  • Separate “manual match”, “ignored with reason”, “needs more evidence” and “confirmed duplicate” decisions if those decisions are supported.

6. Replay and reprocessing

Reprocessing should be deterministic and traceable. Keep the original source identifier, use idempotent ingestion, record the matching-policy version, and avoid mutating historical results without an audit event. If rules change, define whether the operation creates a new evaluation version or replaces a current derived result. Test replay against duplicates, reversals and out-of-order events.

7. Reconciliation quality metrics

  • Match rate with a clearly defined denominator and time window.
  • Exception count and aging distribution.
  • Amount/value of unmatched items, using a defined currency aggregation strategy.
  • Duplicate and malformed input rates.
  • Time from ingestion to completed evaluation.
  • Manual resolution rate and resolution age.
  • Reprocessing volume and policy-version distribution.
  • Source feed freshness and completeness.

Never present a ratio without explaining its denominator, date range, timezone, excluded states and source completeness. A sudden increase in match rate may reflect missing data rather than improved reconciliation.

8. API and Dashboard access

Use OpenAPI to confirm the available transaction and reconciliation operations. Developers manage enabled access workflows at developers.pesaguard.co.ke; the actual business operation runs through api.pesaguard.co.ke. The Customer Dashboard at app.pesaguard.co.ke should call authenticated backend operations and never decide a financial match solely in browser code.
