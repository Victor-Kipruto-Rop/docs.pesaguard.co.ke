Concepts · System architecture

How the PesaGuard platforms work together

PesaGuard is one reconciliation product with separate user experiences and a shared, server-enforced business layer. Each domain has a distinct responsibility. This guide explains the boundaries, the request lifecycle, and how to build against the actual API contract without assuming that a planned capability is already live.

Start here: use developers.pesaguard.co.ke to manage developer access where the relevant workflows are available; use the published OpenAPI contract to confirm operations and schemas; send API requests only to the documented https://api.pesaguard.co.ke origin. A link to a domain is not proof that DNS, authentication, or a particular endpoint is currently available.

The Developer Platform and Dashboard are clients of backend capabilities. They can have their own frontend and account-management services, but transaction and reconciliation rules must remain enforced server-side. Do not create a second transaction database just to support a frontend.

3. Developer integration lifecycle

  1. Read the contract. Start with the OpenAPI reference. Check the exact path, method, authentication requirement, request schema, response schema, and documented errors before writing code.
  2. Open the Developer Platform. Visit developers.pesaguard.co.ke for account and credential workflows. Availability of project management, key creation, sandbox tools, and production requests depends on what is actually enabled for your account.
  3. Obtain a credential through the authorized process. Use the credential type and header specified by the endpoint. Do not assume every endpoint accepts the same credential or that every generated key has the same scope.
  4. Choose the correct environment. Sandbox or staging data must remain isolated from production. Do not send live financial instructions to a test environment or test fixtures to production.
  5. Make a minimal request. Use the examples in the endpoint documentation and send the request over HTTPS to the API origin and path specified by the contract.
  6. Handle the result safely. Parse the documented response schema, preserve transaction identifiers, and distinguish request acceptance from final processing or settlement.
  7. Subscribe to events when supported. If a webhook event is documented and enabled, verify its signature, deduplicate deliveries, acknowledge quickly, and make processing idempotent. Continue to support status queries where the contract requires them.
  8. Validate before production. Test authorization failures, invalid input, duplicate submissions, timeouts, retries, webhook replay, and tenant isolation. Request production access through the approved process rather than assuming a sandbox credential can be upgraded automatically.

4. What happens during an API request

  1. Transport: the client connects to the documented HTTPS API origin and sends the method, path, headers, and body required by the contract.
  2. Authentication: the server validates the credential or session using the authentication scheme actually configured for that endpoint.
  3. Authorization: the server evaluates the principal's permissions, environment, tenant association, resource ownership, and any required scopes.
  4. Validation: input is checked for type, format, required fields, business invariants, and replay/idempotency conditions where applicable.
  5. Execution: the authorized business operation is processed synchronously or queued if the contract defines asynchronous behavior.
  6. Persistence and audit: the service records the authoritative state transition and security-relevant action using the backend's implemented controls.
  7. Response: the API returns the documented status code, response schema, and request/trace identifier where provided.
  8. Follow-up: the client may query a documented status resource or receive a configured webhook. It must not treat an HTTP success response as proof of settlement unless the response contract explicitly says so.

5. How the Customer Dashboard uses the Core API

The Dashboard is the business user's workspace; it is not a privileged shortcut around the API. A finance officer opens a transaction list, the frontend makes an authenticated request, and the backend returns only records that the signed-in user is allowed to see. When the user resolves an exception, the frontend submits a command; the server rechecks authorization and business rules, persists the outcome, and records the action.

For this model to be safe:

  • Every query and mutation must be scoped to the authenticated user's authorized tenant and resources.
  • Never trust a tenant ID, role, amount, reconciliation outcome, or approval decision merely because the browser submitted it.
  • Do not embed privileged server-to-server API secrets in browser JavaScript, HTML, source maps, or downloadable assets.
  • Use the authentication flow actually implemented by the Dashboard and API; cookie-based sessions may require CSRF protection, while bearer-token flows require secure token storage and lifecycle controls.
  • Display the difference between received, validated, matched, exception, failed, reversed, and settled states only when those states are defined by the product contract.
  • Use server-side pagination and filtering for large transaction histories; avoid downloading an entire tenant ledger into the browser.

See Reconciliation concepts, Authentication, and Reconciliation reports.

6. API keys, scopes, and environments

An API key is a credential, not an implementation of authorization by itself. The server must validate the key and determine what it is allowed to do. A secure credential lifecycle includes controlled creation, one-time secret display where applicable, safe storage, narrow scopes, expiry where supported, last-used metadata, rotation, revocation, and audit records.

  • Sandbox: use synthetic or explicitly isolated test data. Sandbox credentials must not read or mutate production records.
  • Staging: use only when an isolated staging environment is actually provisioned. Do not describe staging as available simply because it appears in a design.
  • Production: access must be explicitly provisioned and limited to the approved project, tenant, scopes, and workload.
  • Rotation: create and deploy a replacement credential before revoking the old one when the supported workflow permits overlap; verify the replacement, then revoke the old credential.
  • Exposure: store secrets in a server-side environment or secrets manager. Never commit them, put them in query strings, paste them into support tickets, or expose them in frontend code.

Use API key guidance, authentication guidance, and environment documentation. The exact credential type and header must match the endpoint's OpenAPI security definition and current deployment.

7. Transaction and reconciliation data flow

A payment or ledger record enters through a supported integration or authorized API operation. The service validates its origin and shape, normalizes fields into the canonical model, applies duplicate/idempotency controls, and stores the transaction. Reconciliation then compares the available payment evidence with the expected transaction or ledger record using the matching rules configured for that workflow.

A reconciliation outcome should be explainable. Preserve the source identifiers, matching criteria or reason codes where implemented, timestamps, amounts and currencies, and an audit trail of human overrides. An unmatched item is an exception to investigate; it is not by itself proof of fraud. A matched payment is not automatically proof that funds have settled. Settlement status must come from the relevant authoritative evidence.

For implementation details, see Reconciliation, First reconciliation walkthrough, and Reconciliation reports. Only describe M-Pesa, banks, POS, or other rails as available when their current integration is verified; label planned connectors clearly.

8. Webhooks and asynchronous work

Webhooks let an integration learn that a supported event occurred without continuously polling. They are a delivery mechanism, not the source of truth: a consumer should verify the signature and timestamp where defined, reject invalid or stale signatures, deduplicate event IDs, persist the delivery before acknowledging, and process work asynchronously. Design for retries and duplicate delivery.

For a long-running operation, follow the contract's documented job/status mechanism. A timeout does not necessarily mean the operation failed; before resubmitting a mutating request, follow the documented idempotency behavior and check the status where possible.

See Webhook documentation, reconciliation completion events, and Error handling. Never invent an event name, signature header, retry schedule, or status endpoint that is not in the published contract.

9. Which source is authoritative?

  • API paths, methods, request/response schemas, and security schemes: the checked-in OpenAPI contract, cross-checked against the current deployed API contract when accessible.
  • Creating or managing developer credentials and integration projects: Developer Platform, subject to the features actually enabled.
  • Request execution and business rules: the server-side implementation behind api.pesaguard.co.ke.
  • Customer-facing operations: the Dashboard at app.pesaguard.co.ke, with access and mutations enforced by the backend.
  • Service incidents: status.pesaguard.co.ke, if the status service is deployed and publishing current data.
  • Explanations and integration examples: this documentation site. If an example conflicts with the OpenAPI contract or actual API behavior, report it and follow the verified contract while the documentation is corrected.

10. Production integration checklist

  • Confirm the API origin, TLS certificate, DNS, and environment with the integration owner.
  • Verify the exact endpoint and schema in OpenAPI; do not infer routes from a UI label or a guessed URL.
  • Use a server-side secret store and least-privilege credentials.
  • Test unauthorized, forbidden, invalid-input, rate-limited, duplicate, timeout, and server-error responses.
  • Use idempotency and safe retry rules exactly as documented for each mutation.
  • Implement webhook signature verification, deduplication, durable acknowledgement, and retry-safe processing where webhooks are available.
  • Log request IDs and non-sensitive diagnostics; never log secrets or unnecessary financial/personal data.
  • Validate tenant isolation with tests that prove one customer cannot access another customer's records.
  • Test backup/restore and operational recovery separately from application happy-path tests.
  • Confirm monitoring, incident contacts, key revocation, and production approval before sending live traffic.
  • Run the repository's documentation and OpenAPI checks so examples and links do not drift from the published contract.
