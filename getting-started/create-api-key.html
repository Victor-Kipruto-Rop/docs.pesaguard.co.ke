Getting started

Create an API key

The backend registers API-key lifecycle routes under /auth/api-keys, but the checked-in OpenAPI mirror predates these mounted routes. Use the authorized operator workflow until the deployed contract confirms the endpoint, permissions, and tenant self-service policy. A key record is tenant-bound and carries a role, explicit scopes, active/revocation state, optional expiry, and last-used metadata.

One integration, one credential

Separate keys make ownership, rotation, incident response and usage review possible.

What a credential carries

PropertyBehaviour
scopesThe allowed scope list is intersected with permissions granted to the key's role. An authenticated request without the required permission is denied.
tenantThe key principal is associated with its stored tenant. Routes must still apply that tenant context to the requested resource.
expiryExpiry is optional in the key record. Set a finite expiration as an issuance policy and record the rotation date.
last_usedRecorded, so dormant credentials are visible in review.
StorageThe verifier looks up a SHA-256 digest rather than the submitted plaintext key. Protect the secret in transit and in operator tooling.

Issuance procedure

The backend source registers key lifecycle routes under /auth/api-keys, including create, rotate and revoke operations. The checked-in OpenAPI mirror predates these mounted routes and does not yet provide a verified request/response or permission contract. Until the generated contract is refreshed and confirmed against the deployed revision, use the deployment operator's approved provisioning workflow rather than calling undocumented routes directly.

  1. Use the authorized provisioning workflow and confirm whether the target deployment permits tenant self-service; do not infer access from the existence of a route.
  2. Document the integration owner, tenant, environment, required operations, and least-privilege role/scopes.
  3. Set a finite expiry and rotation date in the provisioning policy; expiry is not mandatory in the underlying record.
  4. Transfer the value through an approved secret-sharing or secret-management workflow and store it server-side.
  5. Record the key identifier and owner, never the raw secret. Validate it with a read-only request in the intended tenant.

Handling rules

  • Keep credentials out of source control. The infra README requires the deployment's .env to be ignored: the same rule applies to your integration's secrets.
  • Use a distinct credential for each integration and environment so revocation has a contained impact.
  • Rotate on a schedule and immediately on suspicion. Verify the old credential is rejected after revocation.
  • Do not include keys in audit details or logs; inspect the actual logging path before handling any sensitive value.

Rotation procedure

Issue the replacement before revoking the current key, deploy it, observe successful traffic, then revoke the old key and verify failure. If compromise is suspected, revoke immediately and accept a controlled interruption rather than leaving an exposed key active.

Deployment policy must be verified

The backend registers key lifecycle routes, but the published OpenAPI mirror is stale and route availability does not establish that self-service issuance or rotation is enabled for your tenant. Until the deployed contract and authorization policy are verified, ask the team that runs your deployment and record the requested scope list.
