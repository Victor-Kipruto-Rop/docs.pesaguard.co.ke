Getting started

First reconciliation

Follow one staging payment past matching: see the reconciliation outcome, read a discrepancy with its explicit reason, and resolve it with an auditable operator decision. Run every step in staging first.

Before you start

  • Complete first transaction — you need a staging payment that already flows end to end.
  • A staging credential with read access and the discrepancy-resolution permission, issued by your pilot admin. Scopes are covered in authentication.
  • Environment variables PESAGUARD_API_URL and PESAGUARD_ACCESS_TOKEN set for staging, as in first request.
Staging first

Reconciliation decisions are financial decisions. Prove the full match-and-resolve cycle in staging before pointing anything at production.

1 · Trigger one payment

Use the first transaction runbook to push one Daraja payment through the staging deployment. Keep its reference, amount and timestamps — they are the keys you will match against.

2 · Watch the matching decision

The reconciliation engine compares the provider event with internal records using deterministic rules — amount, reference, currency and time window. The outcome is one of: matched with evidence, partially matched, or unmatched with a reason. Differences are never smoothed over; a KES 500 delta becomes an exception with the delta stated. The matching sequence is described in reconciliation.

3 · Read the discrepancy queue

Unmatched and mismatched items surface as discrepancies. List them with the operation documented in the checked-in contract:

GET/discrepancies
curl --fail "$PESAGUARD_API_URL/discrepancies" \
  -H "Authorization: Bearer $PESAGUARD_ACCESS_TOKEN" \
  -H "Accept: application/json"

The deployment contract documents the advanced filters available on this route; the running deployment's /openapi.json is authoritative for parameters and response shape. Do not re-implement matching in the client — read the server's outcome instead.

4 · Investigate one discrepancy

  1. Confirm the reason attached to the item — unmatched, amount mismatch, reference not found — and the delta, if any.
  2. Correlate the provider event identity and internal record id; both sides of the comparison stay traceable.
  3. Check the audit trail for anything already decided about these ids. Never guess around an existing decision.
  4. Decide the correct action: fix source data, await a late callback, or resolve explicitly.

5 · Resolve with an auditable decision

Resolution is an explicit operator action, recorded with its reason — not an override of the matching engine. Resolve a single item with POST /discrepancies/{discrepancy_id}/resolve; bulk resolution via POST /discrepancies/bulk-resolve exists for reviewed batches and should be used deliberately, never as a sweep. Required fields for the resolve call come from your deployment's OpenAPI document.

Never force a match

Do not edit financial records to make a mismatch disappear. If the data is wrong, correct the source and let the rules re-run; if the data is right, record the resolution with its reason. Every reconciliation decision must remain explainable later.

6 · Verify the outcome

  1. The transaction's lifecycle state reflects the resolution — see transaction lifecycle.
  2. The audit trail carries the operator decision with tenant and actor context — see audit trails.
  3. If you subscribe to webhooks, the outcome surfaces through the reconciliation.completed event family.
  4. A repeat of the same run produces the same result — safe re-runs are a core guarantee, see idempotency.
