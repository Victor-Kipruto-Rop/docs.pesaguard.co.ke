Getting started

First webhook

Receive one signed delivery in staging and prove that your receiver verifies the sender, accepts durably, handles duplicates and survives replay — before any of this matters in production.

Prove the receiver, not just the platform

A webhook consumer is an independent reliability boundary. These steps establish that boundary with a real staging delivery.

VERIFYACKNOWLEDGEREPLAY
Prerequisites

A staging receiver you control, the staging signing secret from protected storage, and an environment you can restart safely. See test environment and webhook testing.

1 · Publish the receiver

The receiver URL and its staging signing secret are provisioned with the environment rather than through a self-serve form. Keep the secret in protected storage on the receiver side; never embed it in client code, logs or examples.

2 · Verify the sender before parsing

  1. Read the signature header from the delivery.
  2. Recompute the signature over the raw body using the staging signing secret and the documented algorithm — do not reserialize the JSON first.
  3. Compare with a constant-time comparison and reject a mismatch with 401 before parsing or any business logic.
Fail closed

An unsigned or unverifiable delivery is not a degraded delivery — it is untrusted input. Reject it and record the verification outcome without logging the secret or the full signature.

3 · Persist, then acknowledge

Acknowledge with a 2xx only after the event is durably stored on your side. Every attempt is recorded with its outcome; a delivery that times out or errors is retried with bounded backoff and retained in a dead-letter path when retries are exhausted.

The event envelope

Deliveries carry a stable event and delivery identity. The exact payload schema comes from the deployment's OpenAPI document; treat unknown fields as additive.

{
  "id": "event_01J...",
  "type": "transaction.matched",
  "tenant_id": "tenant_123",
  "occurred_at": "2026-09-20T12:00:00Z",
  "data": {},
  "delivery_id": "delivery_01J..."
}

4 · Prove idempotent handling

Deliver the same event twice. The receiver must end with one durable event and one downstream effect — retries and replays must never create duplicate financial effects. Use the event and delivery identity as the deduplication key. See idempotency.

5 · Exercise failure and replay

  1. Force the receiver to fail — stop the process or return 5xx.
  2. Observe bounded retries, then the delivery landing in the dead-letter path with its identity intact.
  3. Replay the event and confirm the final state matches the original successful run.
