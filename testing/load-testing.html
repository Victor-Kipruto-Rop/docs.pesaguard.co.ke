Testing

Load and stress testing

Reconciliation correctness under load is observed, never assumed. Load testing proves that throughput, retries and recovery behave the way the integration requires — start in staging with synthetic data, and use production only when explicitly authorized and confirmed.

Ground rules
  • Staging is the default. Production tests require the appropriate project permission and a separate, explicit confirmation that shows the target, maximum concurrency, maximum RPS and duration.
  • Target only approved project environments and load-test-safe API routes. Never use real financial operations, customer payments, SMS, email, third-party charges, or destructive actions.
  • Synthetic data only — synthetic references, amounts and identities; never production credentials or copied personal data.
  • Schedule the window with the pilot team so observability and consumers are watching.
  • Respect documented rate limits. A 429 under load is backpressure working, not an error to defeat.

What to measure

Decide the signal set before the first request. A load test that only reports request throughput proves nothing about reconciliation correctness.

SignalWhy it matters
API latency and error rateService responsiveness and failure mode per load step.
429 rateWhere backpressure engages; whether clients back off correctly.
Webhook delivery lagEnd-to-end freshness from payment to your receiver.
Consumer lag and dead-letter depthWhether asynchronous processing keeps up or queues pain for later.
Reconciliation latencyTime from provider event to a durable matched/unmatched outcome.
Idempotency proofReplayed inputs under load still produce exactly one durable effect.

Procedure

  1. Baseline — record latency, error rate and reconciliation latency at nominal load with no injected stress.
  2. Ramp — step the load up in stages. Watch where latency bends and whether 429/5xx behavior matches rate limits and error semantics.
  3. Soak — hold a sustained moderate load long enough to expose leaks, unbounded queues and drift in consumer lag.
  4. Spike — push briefly past target volume and confirm the system sheds load safely instead of corrupting state.
  5. Recover — return to baseline and prove recovery: no duplicate financial effects, exceptions still raised with reasons, dead letters present with identity intact and drained deliberately.

Assertions that matter

  • Duplicate submissions under load produce one durable transaction and one logical audit outcome.
  • Concurrent tenants never observe each other's rows — re-run the tenant-safety tests after the run.
  • Reconciliation outcomes at load match the test transaction matrix: matches, mismatches and unmatched all keep their evidence.
  • Nothing is silently dropped: failed items are retried, quarantined or dead-lettered — never discarded.
