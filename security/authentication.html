Security

Authentication Live

PesaGuard supports short-lived JWT bearer access tokens and tenant-scoped API keys on protected API routes. Provider callbacks use the verification method configured for that integration; do not treat callback authentication as interchangeable with API user authentication.

Bearer access tokens

Protected endpoints accept a token in the standard Authorization: Bearer <token> header. The verifier checks the JWT signature with the configured signing key, requires the configured issuer and audience, validates expiry and not-before timestamps, and requires identity, tenant, token type, authorization-version, scope, and token-ID claims. The accepted algorithm is pinned by the backend; the algorithm is not selected from an untrusted token header.

Access-token lifetime is configurable from 1 to 15 minutes and defaults to 15 minutes. Key IDs support verification against configured keys while a signing-key rotation is in progress. The token ID is checked against revocation state, and user tokens are also checked against current account and session state. Machine-principal tokens are checked against the current identity status, tenant and authorization version.

Request example

curl --fail-with-body \
  -H "Authorization: Bearer $PESAGUARD_ACCESS_TOKEN" \
  -H "Accept: application/json" \
  "https://api.pesaguard.co.ke/api/v1/transactions"

Keep access tokens in process memory where practical; never place them in a URL, browser history, source control, screenshots, or logs. Send them only over HTTPS and only to the intended API origin.

API-key authentication

Where an endpoint supports API keys, send the key in X-API-Key. Keys are tenant-bound and resolved using a SHA-256 digest. Their records include a role, an explicit scope list, an active/revoked state, optional expiry, and last-used time. The verifier intersects the permissions associated with the role and the key's explicit scopes; having a key does not grant every permission in the role.

Use a different key for each application or integration. Restrict access to the smallest permitted scope, store the key in a secret manager, avoid printing it in diagnostics, and revoke it immediately if it may have been exposed. See API key security for lifecycle and incident guidance.

Interactive users and sessions

User JWTs are linked to persisted account and session state. Session checks include active state and expiry information, including the configured idle timeout. Refresh tokens are persisted and rotated; reuse of an already-rotated token causes the associated token family to be revoked. Clients should replace a refresh token atomically after a successful refresh and discard the old value.

Provider callbacks are a separate trust boundary

Callback verification is provider-specific. Some flows validate an HMAC over the raw request body; the Daraja callback guard can require a shared-secret header, an IP/CIDR allowlist, or both, and rejects requests when neither is configured. Timestamp/replay checks are supported by the communications delivery callback pipeline where the provider sends a timestamp. Check the relevant integration guide before implementing a receiver.

Failure behavior and operations

  • Missing, malformed, expired, revoked, or invalid credentials are rejected; protected routes do not treat a bad token as an anonymous request.
  • If persisted authentication or revocation state cannot be checked, the API returns an unavailable response rather than silently treating the identity as valid.
  • Configure a unique production JWT_SECRET_KEY of at least 32 bytes. If using a key ring, configure JWT_KEYS_JSON and JWT_ACTIVE_KID consistently before switching the active signing key.
  • Keep PESAGUARD_ALLOW_INSECURE_DEV_SECRET disabled in production; the development fallback is intentionally guarded against production environments.
  • Set session idle timeout and access-token lifetime deliberately, monitor authentication denials, and rehearse revocation before onboarding production integrations.

The exact routes that require authentication are determined by the route configuration and deployment settings. The API's health and documentation routes may have intentionally different exposure rules; review PESAGUARD_PUBLIC_API_DOCS and the production route policy before deployment.
