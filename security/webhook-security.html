Security

Webhook security Live

PesaGuard has separate controls for outbound webhook delivery and inbound provider callbacks. The sender signs outbound deliveries and validates destination URLs; inbound flows authenticate the provider according to the integration. Apply the matching verification procedure at each boundary.

Outbound deliveries

Webhook registration requires an HTTPS URL. The backend resolves the host and rejects private, loopback, link-local, reserved, multicast, unspecified, and selected metadata destinations. It repeats URL validation before each delivery to reduce risk from a hostname whose DNS answer changes after registration. HTTP redirects are not followed; a redirect response aborts that delivery attempt rather than forwarding the event to another host.

Each webhook receives a generated signing secret when registered. The signature is HMAC-SHA-256 over the timestamp, a dot, and canonical JSON (JSON keys sorted recursively with compact separators), encoded in the header as t=<unix-seconds>,v1=<hex-digest>. The request also includes X-Webhook-Event and X-Webhook-Timestamp. The delivery implementation uses a 10-second default timeout and three default attempts, caps configured timeout and retry counts, and backs off between retries.

Receiver verification sequence

  1. Read the exact X-Webhook-Timestamp and signature values; reject missing or malformed headers.
  2. Parse the event JSON, serialize it with the same canonical rules (recursively sorted keys and compact separators), and reconstruct timestamp + "." + canonical_json.
  3. Compute HMAC-SHA-256 using the signing secret provisioned for that endpoint and compare the supplied digest in constant time.
  4. Enforce an acceptable timestamp window using your receiver's clock, then record the event ID and reject duplicate processing idempotently.
  5. Only after successful verification, validate the event schema and apply the business action. Keep the signing secret and received payload out of logs.

Do not assume a generic raw-body signature example matches the outbound canonical-JSON format. Use the exact verification contract for your deployment and test against a real non-production delivery. See Webhook signature verification.

Inbound callbacks

Inbound providers do not all use the outbound signing scheme. The communications delivery callback path verifies an HMAC-SHA-256 digest of the raw request bytes, accepts a provider-specific signature header format, and checks timestamps when supplied. Its default maximum age is five minutes. Duplicate provider event IDs are detected before the event is applied again.

The Daraja callback guard can require a configured shared-secret header, an IP/CIDR allowlist, or both. If neither is configured, it rejects the callback by default. If forwarded client addresses are used, configure PESAGUARD_TRUSTED_PROXY_COUNT to match the actual proxy chain; otherwise the code uses the direct peer address. Never trust a client-supplied forwarded-for header from an untrusted network.

Operator controls and limitations

  • Keep secrets unique per webhook/integration, restrict who can read them, and rotate them after a suspected disclosure.
  • Ensure egress policy independently restricts destinations. URL validation is an application control and should not replace network-level egress controls.
  • Use idempotent event handling: retries are expected, and a sender cannot know whether a receiver committed an action before a connection failed.
  • Monitor failed deliveries and replay queues without exposing full payloads or authentication headers in logs.
  • Do not treat DNS revalidation alone as a complete guarantee against every DNS rebinding or network-path threat; validate behavior in the deployed network.

Implementation evidence includes webhook_manager.py for outbound delivery and communications/webhooks.py plus security_helpers.py for inbound verification paths. These flows use different formats and must not be conflated.
