Security

Tenant isolation Live

Tenant isolation binds an authenticated principal to an authorized tenant and requires that context to constrain every tenant-owned operation. The application provides tenant and resource authorization helpers, but isolation must be preserved across each route, query, asynchronous job, export, cache, and administrative workflow.

Identity and tenant context

Verified user and machine identities carry a tenant identifier. API-key records are tenant-bound, and machine-principal records are resolved with both identity and tenant. The tenant ID supplied in a URL, query parameter, or JSON body is an object of authorization to check; it is never sufficient evidence of permission by itself.

Protected routes can use tenant-access checks to compare the requested tenant with the principal's tenant. Cross-tenant access is a separately granted permission (for example, manage:all_tenants); it should be assigned only to an explicitly approved operational role. Resource-scoped guards also bind a permission to the resource ID rather than relying only on a broad route-level check.

Apply the boundary end to end

  • Reads and writes: include the authorized tenant in database predicates for both lookup and mutation; do not fetch globally and filter only in the response layer.
  • Related records: verify that referenced provider, webhook, transaction, user, and organization records belong to the same authorized tenant before joining or mutating them.
  • Background work: persist the tenant with queued jobs and events, then re-check it at consumption, replay, retry, and dead-letter operations.
  • Derived data: include tenant scope in cache keys, analytics aggregates, search indexes, report files, export objects, and idempotency/replay identifiers.
  • Administration: require explicit cross-tenant authorization, record the actor and reason, constrain the operation to its approved scope, and review the result.

Failure behavior

Missing or malformed tenant context should be rejected. A cross-tenant request should not return the protected record. Depending on the route contract, it may return 403 or an intentionally non-disclosing 404; do not assume that every endpoint uses the same response code. If current authorization state cannot be loaded, sensitive operations should fail closed with an unavailable response rather than proceed using a caller-selected tenant.

Verification strategy

  1. Create at least two test tenants with distinct records and principals.
  2. For every read, write, list, export, and replay endpoint, verify that a tenant can access its own records and cannot read, update, delete, count, or infer another tenant's records.
  3. Repeat tests with tenant IDs in path, query, and request body, including conflicting identifiers and missing values.
  4. Exercise asynchronous consumers, retries, webhook deliveries, caches, and report-generation jobs; test cross-tenant references as well as direct IDs.
  5. Verify that an explicitly authorized cross-tenant administrative action is logged and that an ordinary administrator or tenant role cannot invoke it by changing request data.

The backend repository contains tenant-scoped checks and test suites for authorization and data access. A load test across 100 tenants is not a substitute for route-by-route security testing; no database row-level security guarantee is claimed here unless it is separately configured and verified in your deployment.
