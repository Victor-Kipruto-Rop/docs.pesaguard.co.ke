Security

Security Live

This section describes security controls visible in the PesaGuard backend, the evidence available in its code and tests, and the deployment responsibilities that cannot be verified from source alone. A control marked live is not a certification or a guarantee about every customer deployment.

Control areaImplemented behaviourDeployment or operator responsibility
AuthenticationJWT verification checks signature, issuer, audience, time claims, token identifier, tenant and current account/session state. API keys are resolved by digest.Use production signing keys, protect them, and review authentication requirements on each exposed route.
AuthorizationProtected routes can enforce named permissions, tenant access and resource-level permissions server-side.Assign only the roles and scopes each identity needs; review elevated access and service identities.
API keysTenant-bound records carry role, scopes, expiry/revocation state and a SHA-256 key digest.Store credentials in a secret manager, set expiry where appropriate, rotate and revoke promptly.
WebhooksOutbound destinations are checked for HTTPS and unsafe addresses; delivery signatures are provided. Inbound flows validate their configured authentication.Verify signatures before processing, reject stale/replayed events where timestamps are available, and keep receiver endpoints patched.
EncryptionApplication helpers encrypt selected sensitive payload values and provider configuration; HTTPS responses receive HSTS when the app recognizes HTTPS.Configure TLS termination and storage/backup encryption in the hosting environment; protect and rotate encryption keys.
Data protectionAudit details and provider serialization include redaction paths; a versioned retention policy is present in the backend repository.Confirm jobs, storage lifecycle rules, legal holds, and approved deletion are enabled in the deployed environment.
Tenant isolationAuthenticated identity includes tenant context, and route/query helpers can enforce tenant- and resource-scoped access.Pass the authenticated tenant context through every query, cache, export, event, and administrative workflow.
Audit evidenceAudit entries can be append-only, hash-linked, integrity-checked, and optionally signed.Configure signing keys and immutable archive destinations; monitor integrity checks and retention jobs.

How to read these pages

Each page separates the threat, the implemented control, evidence in the backend repository, and steps an operator or integrator can take to verify the behavior. Repository tests establish behavior for the exercised paths; they are not proof that every route, dependency, or production setting has been reviewed.

The API exposes multiple applications and integration flows. Authentication and callback verification therefore vary by route and provider: consult the endpoint contract and the relevant guide rather than assuming one credential or signature scheme applies everywhere.

Deployment boundary

  • Deploy the API behind HTTPS, configure trusted proxy handling deliberately, and set production secrets through a protected secret-management system.
  • Restrict CORS to the intended origins, keep production authentication enabled, and avoid enabling development-only bypasses in production.
  • Backups, database-volume encryption, network segmentation, host patching, key custody, and monitoring depend on the selected infrastructure and are not proven by application source code alone.
  • No third-party security certification is represented here. Ask PesaGuard for deployment-specific assurance information before treating these pages as contractual commitments.

Evidence and verification

  • JWT lifecycle and refresh-token behavior: backend tests in tests/test_auth_lifecycle.py.
  • Authorization enforcement: backend tests in tests/test_rbac_enforcement.py.
  • Audit redaction and append-only behavior: backend tests in tests/test_action_audit.py.
  • Payload encryption and identifier tokenization: backend tests in tests/test_data_protection.py.

For a suspected vulnerability, use the private reporting route on the responsible disclosure page. Do not send credentials, payment data, or customer records in a report.
