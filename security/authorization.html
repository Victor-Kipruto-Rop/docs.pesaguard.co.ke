Security

Authorization Live

Authentication establishes an identity; authorization decides whether that identity may perform a particular action on a particular tenant or resource. Enforcement belongs on the server, not in a client-side menu or button.

Authorization checks

The backend's route guards can enforce a named permission, tenant access, or a resource-specific permission. The caller is resolved from a verified token or API-key record, and the resulting principal carries its tenant, role, and permission set. A request-supplied tenant identifier is not, by itself, proof that the caller may access that tenant.

CheckPurposeTypical failure
Route permissionRequire a named action such as read:transactions or manage:webhooks.403 when the authenticated principal lacks the permission.
Tenant accessBind a requested tenant to the principal's authenticated tenant context, except for explicitly authorized cross-tenant administration.403 when the requested tenant is outside the caller's authority.
Resource accessCheck the permission against the exact resource identifier supplied to the route.403 for a denied resource action; 400 for a missing or malformed resource identifier.
Authorization-state availabilityRequire current role, session, identity, or revocation state where the code path uses persisted state.503 when the decision cannot be made safely.

Roles and permissions

Role names and grants are defined in the backend policy map and can evolve with the product. The implementation includes organization roles such as owner, admin, finance, operations, analyst, and read-only roles; the exact grant list, not the label, determines access. For example, the owner role includes the cross-tenant permission manage:all_tenants, while the admin role's grants are separately enumerated. Do not assume that two roles with similar names are equivalent.

Where a machine credential carries explicit scopes, the effective permission set is constrained by both its assigned role and those scopes. Grant only the operations an integration needs, and review role-to-scope changes as access-control changes rather than routine configuration.

Recommended access-management procedure

  1. Identify the human or service principal that needs access, the tenant it operates in, and the exact actions required.
  2. Choose the narrowest role and, for machine credentials, the narrowest supported scopes. Avoid cross-tenant permissions unless the operational function requires them.
  3. Issue an individual account or integration credential; do not share credentials between people or services.
  4. Review grants after role changes, team changes, integration replacement, and incident response. Revoke unused credentials and sessions promptly.
  5. Test both allowed and denied paths using separate principals. Confirm that missing authorization state fails closed and that denied access is observable without logging secrets.

Audit and verification

Authorization denials are returned distinctly from missing or invalid credentials and security-event instrumentation is present on relevant checks. Administrative actions should be traced through the audit facilities described in Data protection and Audit trails. The repository's tests/test_rbac_enforcement.py exercises a denied privileged-route case; it should be supplemented with deployment-specific checks for each route and role combination you rely on.

Do not interpret an API returning 404 as proof of a particular authorization policy; route and resource behavior can vary. Use the API reference for the documented response contract and test the tenant boundary directly.
