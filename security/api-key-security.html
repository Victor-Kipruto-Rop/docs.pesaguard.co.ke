Security

API key security Live

PesaGuard API keys authenticate machine requests through tenant-bound records. The verifier compares a SHA-256 digest, checks the record's active, revoked and optional expiry state, then limits effective permissions to the intersection of role grants and the key's configured scopes.

How a key is checked

  1. The client sends the key in the X-API-Key request header over HTTPS. Do not put it in a query string or request body.
  2. The API accepts the expected pk_ key prefix, hashes the supplied value with SHA-256, and looks up the matching key record; the plaintext key is not used as the database lookup value.
  3. The record must be active, not revoked, and not expired. A key may have no expiry date if one was not configured, so set an expiry as part of your own issuance policy.
  4. The API derives permissions from the stored role and intersects those with the record's scope list. It updates the last-used time after successful record validation.
  5. The resulting principal remains bound to the tenant recorded for that key. A client cannot change its tenant by adding a different tenant ID to a request.
curl --fail-with-body \
  -H "X-API-Key: $PESAGUARD_API_KEY" \
  -H "Accept: application/json" \
  "https://api.pesaguard.victorkipruto.com/api/v1/transactions"

Issue and store keys safely

  • Create a distinct credential for each environment, application, and integration so an incident can be contained without taking unrelated clients offline.
  • Grant only the scopes required by that integration. Prefer read-only access where writes are unnecessary, and avoid cross-tenant privileges.
  • Store the key in a managed secret store or protected runtime configuration. Limit who and which workloads can read it; do not put it in source control, build logs, screenshots, browser code, tickets, or telemetry.
  • Transmit keys only to the documented API host over HTTPS. Never include a key in a URL, where it can leak through browser history, proxies, analytics, and server access logs.
  • Track the key owner, purpose, tenant, environment, scopes, approver, creation time, expiry, and planned rotation date in your own credential inventory.

Rotation and suspected exposure

  1. Create a replacement key with the same or narrower scopes and an explicit expiry, if the key-management workflow supports parallel credentials.
  2. Update the integration's secret store and deploy the replacement without printing the value.
  3. Confirm successful requests using the replacement, then revoke the old key. Do not leave both credentials active longer than the migration requires.
  4. If a key is exposed, revoke it immediately, identify its tenant and permissions, review recent use and audit/security events, then issue a replacement after containment.

The key record supports active/revoked status, optional expiry, and a rotation predecessor reference in the data model. Exact key-creation routes and available overlap behavior depend on the deployed API version; consult the API reference rather than assuming a management endpoint or automatic rotation schedule.

Failure handling and verification

Invalid, expired, and revoked keys are rejected as authentication failures. If the API cannot safely read the key/revocation state, it returns an authentication-unavailable response rather than authorizing from a cache-free fallback. Test a valid key, an expired key, a revoked key, and a key whose scope excludes the requested operation in a non-production tenant.

Backend implementation evidence includes the ApiKeyRecord model, the tenant-key hardening migration, and API-key verification in auth_rbac.py. The SHA-256 hash is an identifier for a high-entropy generated key; it is not a substitute for limiting access to the record store or protecting the key in transit.
