Security

Encryption Live

The backend contains application-level encryption for provider configuration and selected sensitive payload values. This is distinct from TLS in transit and from storage- or backup-level encryption, which must be configured and verified in the deployment infrastructure.

Application-level field encryption

Provider configuration uses Fernet authenticated encryption for credential-bearing values, stored with an enc:v1: prefix. Sensitive payload handling encrypts configured keys such as phone numbers, account numbers, customer names, national identifiers, and authorization codes while preserving the surrounding JSON structure. Identifier tokenization uses a keyed HMAC-SHA-256 digest for equality lookup without putting the original identifier in the token value.

These helpers protect selected values in application-managed records; they do not establish that every database column, log, exported file, message, database volume, or backup is encrypted. Inspect the actual data path and hosting controls for the data category you use.

Key configuration and rotation

  • Production provider configuration requires PROVIDER_ENCRYPTION_KEY; do not rely on the development fallback.
  • Payload encryption uses PESAGUARD_PAYLOAD_ENCRYPTION_KEY (or the compatibility provider key setting) and can accept a previous key during a rotation window.
  • Keep encryption keys in a managed secret store, restrict read access to the workloads that need them, and never commit them to source or copy them into support tickets.
  • For rotation, deploy the new active key and the previous key together, re-encrypt stored values with the provided rotation operation, verify that all protected data can be read with the new key, and only then remove the previous key.
  • Keep a separately controlled recovery plan for key loss. Ciphertext that cannot be decrypted with any configured key is not recoverable by the application.

Encryption in transit

Use HTTPS for all API, administrative, webhook, and operator traffic. The dashboard API emits HSTS when its request context is recognized as HTTPS. When TLS terminates at a reverse proxy or load balancer, configure trusted proxy behavior correctly and verify the external response headers at the public endpoint; application code cannot prove that every network hop is encrypted.

What this page does not claim

  • It does not claim universal database, disk, object-storage, Kafka, or backup encryption; configure and verify each service's native encryption controls.
  • It does not claim customer-managed keys, a hardware security module, or a centralized vault integration.
  • It does not claim that the same encryption key can safely be reused for JWT signing, field encryption, and unrelated integrations. Use separate secrets for separate purposes.
  • It does not replace access control, data minimization, redaction, retention, or secure key custody.

Verification checklist

  1. In production configuration, confirm the required encryption keys exist and meet the deployment's entropy and custody standards.
  2. Write a test value through the provider/payload path and confirm the persisted sensitive value is ciphertext rather than plaintext.
  3. Confirm the application can decrypt existing records during a planned key rotation, then verify re-encryption and removal of the previous key.
  4. Check the public API endpoint for HTTPS and HSTS, and independently verify encryption for the database, object storage, queues, and backups.
  5. Test restore and decryption from backup using controlled recovery procedures; a backup is not useful if its required keys are unavailable.
