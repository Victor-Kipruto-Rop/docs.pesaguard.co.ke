Webhooks

Verification

PesaGuard outbound webhooks use a timestamped HMAC-SHA-256 signature over canonical JSON. Verify the sender before business processing, enforce a freshness window, and deduplicate accepted event IDs. This format is for PesaGuard outbound webhooks; inbound provider callbacks can use different formats.

  1. Read the timestamp and X-Webhook-Signature header; reject missing or malformed values.
  2. Parse the body as untrusted JSON under a strict size limit and serialize it with recursively sorted keys and compact separators.
  3. Compute HMAC-SHA-256 over timestamp + "." + canonical_json using the endpoint's signing secret.
  4. Compare the hexadecimal digest in constant time, enforce the timestamp window, and process the event idempotently only after verification.
Trust boundary

Parsing is permitted only to reconstruct the documented canonical representation; do not persist, forward, or act on the event until its signature and freshness have been verified.

Signature format

AlgorithmHMAC-SHA-256, represented as lowercase hexadecimal.
Signed bytesUTF-8 encoding of <timestamp>.<canonical_json>.
Canonical JSONJSON serialization with keys sorted recursively and compact separators (no spaces after separators).
Signature headerX-Webhook-Signature: t=<unix-seconds>,v1=<hex-digest>.
Timestamp headerX-Webhook-Timestamp; the same Unix timestamp is included in the signed input.
SecretThe per-endpoint secret provisioned for this webhook. Keep it private and out of logs.

Verification checklist

StepRequirement
Bound inputEnforce a request-size limit and parse JSON as untrusted input without side effects.
Resolve secretUse the environment-specific endpoint signing secret from protected storage.
CanonicalizeSerialize parsed JSON using recursively sorted keys and compact separators, then sign timestamp, dot, and canonical JSON.
CompareUse constant-time digest comparison; reject malformed headers and stale timestamps.
ProcessOnly after verification, deduplicate the event and perform business processing idempotently.

Freshness, duplicates, and failures

Compare the timestamp against the receiver's clock and reject values outside a short configured window (five minutes is a reasonable default if your integration has no stricter agreement). Use synchronized clocks. Store an event identifier or stable deduplication key with the processing result so sender retries do not repeat business effects.

Reject invalid signatures and stale timestamps before persistence or business actions. Record a safe delivery identifier and verification outcome, but never log the shared secret, full authorization material, or sensitive payload. Return a non-success response when verification fails; use the retry guidance to decide receiver behavior for transient failures.

Do not use this procedure for incoming provider callbacks. For example, the communications callback path authenticates the raw request bytes, while Daraja callbacks have separate source-validation settings. See Webhook security for the distinction.
